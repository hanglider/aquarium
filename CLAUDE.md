# Aquarium — консольный симулятор эволюции рыб

## Зачем этот проект

Учебный проект. Главная цель — освоить GitHub как платформу: ветки, pull request'ы,
squash/rebase, Issues, Projects, Actions, релизы, Packages, Pages, security-фичи.
Игра — повод, а не цель. Поэтому:

- код пишешь ты (Claude Code), а **все действия на платформе GitHub делает человек сам**:
  создаёт PR, ревьюит, мержит, ставит теги, публикует релизы, настраивает Settings.
  Не используй `gh pr merge`, `gh release create`, не создавай теги и не трогай настройки репо.
  Если для шага нужно действие на платформе — остановись и опиши, что и где нажать.
- Объясняй по-человечески, прозой. Когда вводишь новую git- или GitHub-механику,
  коротко поясни, зачем она и на чём обычно спотыкаются.
- Иди по одному шагу. Закончил шаг — остановись и жди подтверждения.

## Стек

- Go 1.22+, стандартная библиотека. Внешние зависимости — только когда это запланировано (см. роадмап).
- Отрисовка в терминале через ANSI escape-коды.
- Тесты: стандартный `testing`, симуляция должна быть детерминированной при заданном seed.

Структура:

```
cmd/aquarium/main.go      — флаги, запуск, игровой цикл
internal/sim/             — мир, рыбы, корм, гены, шаг симуляции (без вывода на экран)
internal/render/          — отрисовка состояния в терминал
```

Логика симуляции не должна знать про терминал — так её можно тестировать.

## Git-флоу

### Ветки

- `main` — только выпущенный код. Каждый коммит в main соответствует релизу и помечен тегом `vX.Y.Z`.
- `dev` — интеграционная ветка, сюда сливаются готовые фичи.
- `feature/<issue>-<кратко>` — фича, от свежего `dev`. Пример: `feature/12-reproduction`.
- `fix/<issue>-<кратко>` — исправление бага, тоже от `dev`.
- `hotfix/<кратко>` — срочный фикс уже вышедшей версии: от `main`, PR в `main`, затем `main` сливается обратно в `dev`.

Прямые коммиты в `main` и `dev` запрещены (после первого начального коммита). Всё — через PR.

### Как сливаем

- `feature/*` и `fix/*` → `dev`: **Squash and merge**. Вся ветка превращается в один коммит
  в dev, заголовок = заголовок PR. После мержа ветка удаляется.
- `dev` → `main` (релиз): **Create a merge commit**. Не squash — иначе история main и dev
  разойдётся и при следующем релизе git покажет старые изменения как новые.
- `hotfix/*` → `main`: squash, потом PR `main` → `dev` обычным merge commit.

### Обновление ветки

Если пока фича делалась, `dev` ушёл вперёд — ребейз, а не мерж dev в фичу:

```
git fetch origin
git rebase origin/dev
# решить конфликты, если есть
git push --force-with-lease
```

Force-push допустим только в свою feature/fix-ветку. В `dev` и `main` — никогда.
После squash-мержа в старой ветке больше не работаем: новая фича — новая ветка от обновлённого dev.

### Коммиты и PR

Conventional Commits: `feat: ...`, `fix: ...`, `refactor: ...`, `test: ...`, `docs: ...`, `ci: ...`, `chore: ...`.
Заголовок PR в том же формате — он станет коммитом после squash.
В описании PR: что сделано, как проверить, `Closes #N`.

Перед каждым коммитом: `gofmt -l .` пусто, `go vet ./...` и `go test ./...` зелёные.

### Версии

SemVer. До 1.0.0 новая фича = minor (`v0.2.0`), фикс = patch (`v0.2.1`).

## Роадмап

Каждая версия — milestone на GitHub, каждая фича — отдельный issue и отдельный PR.
Справа — какую часть платформы осваиваем на этом этапе.

### Этап 0 — подготовка
Начальный скелет (go.mod, структура папок, пустой main, CLAUDE.md) — единственный прямой коммит в main.
Затем ветка `dev`.
*Платформа:* default branch, labels, milestones, доска в Projects, шаблоны issue и PR (`.github/`).

### v0.1.0 — живой аквариум
Сетка, рыбы двигаются случайно, корм появляется случайно, рыба ест корм и получает энергию,
каждый шаг тратит энергию, при нуле умирает. Флаги: размер, число рыб, скорость, seed.
Строка статистики: шаг, рыб, корма.
*Платформа:* первый feature-PR и squash; workflow CI (`gofmt`, `vet`, `test`, `build`) на каждый PR;
первый релиз **вручную** через UI, чтобы понять, что такое тег и релиз.

### v0.2.0 — размножение
При запасе энергии рыба делится, энергия делится пополам. Ограничение популяции едой.
*Платформа:* rulesets/branch protection на main и dev (только через PR, зелёный CI обязателен);
workflow релиза: на пуш тега `v*` собирает бинарники под linux/windows/darwin (amd64, arm64)
и сам создаёт релиз с ассетами и сгенерированным changelog.

### v0.3.0 — гены и эволюция
Гены: скорость, дальность зрения, расход энергии. Рыба видит корм в радиусе и плывёт к нему.
Потомок наследует гены с мутацией. В статистике — средние значения генов.
*Платформа:* Dependabot (go modules + actions), CodeQL, secret scanning, `CODEOWNERS`, `SECURITY.md`.

### v0.4.0 — хищники
Второй вид, ест рыб. Отрисовка переходит на библиотеку (например tcell) — первая внешняя зависимость.
*Платформа:* Dockerfile, сборка образа в Actions и публикация в GitHub Packages (ghcr.io);
запуск через `docker run -it`.

### v0.5.0 — статистика и наблюдение
Экспорт статистики в CSV, пауза/шаг по клавишам, сохранение seed.
*Платформа:* GitHub Pages с описанием проекта и графиками эволюции, деплой через environment
`github-pages`; devcontainer для Codespaces; Discussions.

### v1.0.0 — стабильная версия
Чистка, README с гифкой, документация флагов.
*Платформа:* hotfix-флоу на практике, environments с защитой и секретами, финальный релиз.

## Порядок работы над фичей

1. Человек создаёт issue и говорит номер.
2. `git checkout dev && git pull` → `git checkout -b feature/<N>-<кратко>`.
3. Пишешь код небольшими осмысленными коммитами, с тестами на логику `internal/sim`.
4. Проверки, `git push -u origin <ветка>`.
5. Предлагаешь заголовок и описание PR. Человек сам открывает PR, смотрит CI и мержит.
6. Ждёшь подтверждения, что смержено, и только потом берёшь следующую задачу.
